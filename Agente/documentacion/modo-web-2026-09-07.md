# Modo web local `glory-harness web` — operación (069A-2 F6)

Contrato en `cli/src/comandos/web.rs`, `web_turnos.rs`, `web_datos.rs`.
UI en `desktop/ui/src/adaptadores/api.ts` sobre `tauri/real.ts`.

## Arranque

```text
glory-harness web [--puerto 8799] [--dir-ui <ruta>] [--fixture]
```

- `--puerto`: default 8799. `--dir-ui`: sirve la UI compilada desde el mismo
  proceso (mismo origen, sin CORS); sin el flag solo hay API.
- `--fixture`: turnos sintéticos sin proveedor (E2E y humo sin claves).
- Bind fijo `127.0.0.1` (loopback; no hay flag de bind: exponer en red es
  una decisión explícita futura, no un accidente).

## Token y sesiones

- `GLORY_HARNESS_WEB_TOKEN`: token maestro. **Solo crea sesiones**
  (`POST /api/v1/session`); cualquier otro uso → 401 `no_autorizado`.
- Sin la env, el servidor funciona sin token maestro y solo enlaza `127.0.0.1`; la sesión se autoriza con la cookie HttpOnly emitida al crearla.
- La sesión opaca (`session_id` UUID) autoriza por `Bearer <sid>` o cookie
  `gh_sesion` (`HttpOnly`, `SameSite=Lax`, `Path=/`, `Max-Age=86400`).
  `EventSource` no envía `Authorization`: el SSE se autoriza por cookie.
- Mutaciones por cookie exigen mismo origen (`Origin`/`Referer` o ausencia
  total en curl); `SameSite=Lax` bloquea el envío cross-site en navegador.
- TTL 24 h server-side (igual que la cookie): expirada → 410
  `sesion_expirada` + aborto del turno huérfano. Cierre explícito con
  `DELETE /api/v1/session/:id` (cancela el turno activo).
- Tope 16 sesiones vivas (purga perezosa de expiradas al crear) → 429
  `demasiadas_sesiones`. Cuerpo máximo 256 KiB → 413; mensaje 32k chars →
  413 `mensaje_largo`; meta 8k chars → 413 `meta_larga`. Un turno por sesión → 409 `turno_activo`.
- La meta se fija o limpia con `PATCH /api/v1/session/:id/meta`; el valor se
  normaliza y se aplica al siguiente turno en modo `meta`.

## Workspace, SQLite, backup, apagado

- Workspace: ruta absoluta existente (validada, `is_dir`); cambio bloqueado
  durante turnos (409). Sin validación de contenencia: es máquina local del
  propio usuario (documentado, no una sandbox multiusuario).
- SQLite compartida con Tauri/CLI: rusqlite bundled, WAL en fichero,
  `busy_timeout` 5 s; error explícito ante bloqueo, nunca silencioso
  (test `sqlite_compartida_entre_dos_handles`).
- Backup: snapshot del fichero SQLite a nivel de sistema de ficheros con los
  procesos detenidos. No existe endpoint de backup en vivo (no inventarlo).
- Apagado: Ctrl-C / matar el proceso; `DELETE` de sesiones cierra limpio.
  Un turno sin dueño se aborta al expirar su sesión.

## Auditoría de logs (F6, 2026-09-07)

- `web*.rs` emite `eprintln` de arranque (addr + nombre de la env, sin
  valores), fallo de bind y error del servidor. Nunca imprime tokens, cookies
  ni contenido de peticiones.
- Ningún log incluye: valor del token, cookie, `session_id`, cuerpos de
  mensaje, prompts, ni contenido de conversaciones. `servicio/` no loguea.
- El `workspace` viaja en JSON hacia su propio cliente (diseño), no a logs.

## Matriz daemon-TCP vs web-HTTP

| Aspecto        | `daemon` (TCP NDJSON)              | `web` (HTTP+SSE)                          |
|----------------|------------------------------------|-------------------------------------------|
| Env de token   | `GLORY_HARNESS_DAEMON_TOKEN`       | `GLORY_HARNESS_WEB_TOKEN`                 |
| Bind           | `127.0.0.1`                        | `127.0.0.1` fijo                          |
| Apertura       | `sesion_abrir.token` por mensaje   | `Bearer` maestro solo crea                |
| Autorización   | token de sesión por mensaje        | `Bearer <sid>` o cookie `gh_sesion`       |
| Stream         | líneas NDJSON                      | SSE (`event:` + `turn.finished`)          |
| Consumidor     | agentes/harness CI                 | UI navegador/Tauri (misma app)            |

No se unifican los tokens: son dominios de confianza distintos (agente
programático vs UI local); unificar ampliaría el blast radius sin beneficio.
